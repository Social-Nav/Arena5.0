# Scenario 与社交行为 Profile 配置说明

适用于 `worlds/<world>/scenarios/<name>/scenario.yaml` 与
`configs/nav2/profiles/<name>/profile.yaml`。


---

## 1. 文件结构

```yaml
dynamic:                  # 行人列表
- name: hunav_1
  model: female_adult_business_02
  pose: [x, y, yaw_deg]
  behavior_tree: BTRegularNav.xml
  behavior:
    type: 1
    social_force_factor: 10.0
  desired_velocity: 1.05
  waypoints:
  - pose: [x, y, heading_deg]
    desired_velocity: 0.8
robot:                    # 亦可写作 robots:（列表）或 start/goal 形式
  name: robot
  pose: [x, y, yaw_deg]
  social_attributes: neutral
  social_yielding: false
  desired_linear_vel: 0.5
  waypoint_tolerance: 0.30
  final_goal_tolerance: 0.15
  waypoints:
  - [x, y, yaw_deg]
```

角度与坐标：

- `pose` 第 3 个元素为**角度制** yaw，行人与机器人一致。
- 行人 waypoint 的第 3 个元素会被丢弃。SFM 下行人朝向由速度方向涌现，每 tick 重新计算，
  逐点朝向无意义。
- 机器人 waypoint 的第 3 个元素会作为该段 Nav2 goal 的目标 yaw。
- 行人的 `z` 被忽略，固定为 1.25 m。

另有 `static:`（静态障碍物，字段 `name` / `model` / `pose` / `scale`）与旧格式 `obstacles:`
（其下再分 `static` / `interactive` / `dynamic`，后者两类被合并处理）。现有 174 个 scenario
均未使用。注意其 `pose` 第 3 个元素仍按**弧度**解析，与行人机器人不一致，启用前需先统一。

`configs/task_generator.yaml` 与 benchmark suites 中的 `interactive` 属于随机任务模式，
不读取 scenario 文件。

## 2. 行人字段

| 字段 | 说明 |
|---|---|
| `name` | 唯一字符串，惯用 `hunav_N`。 |
| `model` | 仅影响外观。可用值见下。 |
| `pose` | 出生位姿 `[x, y, yaw_deg]`。 |
| `behavior_tree` | 决定行为，见 §3。 |
| `behavior` | 力增益与行为树端口，见 §4。 |
| `desired_velocity` | 默认速度（m/s）；waypoint 未覆盖速度时使用。 |
| `velocity` | **不生效**，代码从不读取，可省略。 |
| `waypoints` | 目标点列表，按序访问；格式见下。 |
| `radius` | SFM 二维身体半径，当前默认 0.42 m；参与 agent 表面距离和社交避让。与 `behavior:` 同级书写。 |
| `look_ahead` | Isaac 人物临时行走目标的投影距离，默认 2.0 m；不是扫描距离或行为触发距离。 |
| `cyclic_goals` | 循环开关，当前默认 false；可由每个行人单独覆盖。 |
| `goal_radius` | 目标到达半径，默认 0.2 m；实际判定还额外加 0.1 m。 |

`waypoints` 兼容三种写法。速度必须大于 0，表示“从上一点移动到当前目标点”这一段的期望速度：

```yaml
waypoints:
- [1.0, 2.0, 90.0]                         # 旧格式：使用顶层 desired_velocity
- [2.0, 2.0, 0.0, 0.7]                    # 紧凑格式：第 4 维为该段速度
- pose: [3.0, 2.0, 0.0]                    # 推荐格式
  desired_velocity: 0.5
```

`cyclic_goals: false` 时按 `W1 -> W2 -> W3` 行走；到达判定为
`distance <= goal_radius + 0.1 m`。行人被判定到达最后一个 waypoint 后会清零期望速度、当前
速度、角速度和全部 SFM 力，并保持原地停止。`cyclic_goals: true` 时 Arena 会先把路线扩展为
往返序列（例如 `W1 -> W2 -> W3 -> W2 -> W1 -> 出生点`），再由 HuNav 循环执行。

当前完整 `pedestrian` 人物池的 22 个 identity 静态 USD 水平身体参考半径约为
`0.25～0.417 m`，中位数 `0.362 m`、P90 `0.399 m`。当前统一默认值为 `0.42 m`，是保守的
二维近似，不是每个 USD 的精确动态包络。Isaac 侧另有半径 `0.5 m` 的 LiDAR 感知代理，
它只扩大机器人看到的行人障碍，不会自动改变 HuNav 的 SFM radius。

可用模型（其余取值将被随机替换）：`female_adult_business_02`、`female_adult_medical_01`、
`female_adult_police_01..03`、`male_adult_construction_01/02/03/05`、`male_adult_medical_01`、
`male_adult_police_04`。

未声明的字段回退至 `arena_bringup/configs/hunav/default.yaml`。

## 3. 行为

行为由 `behavior_tree` 决定，`type` 不决定行为，但**两者必须一致**，否则会出现运行某棵树而
受力逻辑属于另一棵树的行人。

| `type` | 名称 | 行为树 | 行为 |
|---|---|---|---|
| 1 | REGULAR | `BTRegularNav.xml` | 沿既定路线行走，将机器人视作另一行人 |
| 2 | IMPASSIVE | — | 将机器人视作静态障碍物，不做社交避让 |
| 3 | SURPRISED | `BTSurprisedNav.xml` | 察觉机器人后停止并转向注视 |
| 4 | SCARED | `BTScaredNav.xml` | 降速并远离机器人 |
| 5 | CURIOUS | `BTCuriousNav.xml` | 靠近机器人，至一定距离停止 |
| 6 | THREATENING | `BTThreateningNav.xml` | 抢至机器人前方阻挡 |

机器人如何进入行人的受力计算，取决于当前 tick 是否处于特殊状态（由行为树在触发时置位）：

| type | 特殊状态激活时 | 未激活时 |
|---|---|---|
| 1 REGULAR | 作为行人参与社交力求和 | 作为行人 |
| 2 IMPASSIVE | 作为**障碍物** | 作为行人 |
| 3–6 | **不参与受力** | 作为行人 |

即 type 3–6 的行人平时仍受机器人社交力，仅在特殊行为触发的那一 tick 排除机器人；impassive
也并非始终将机器人视作障碍物。这些类型的主导机制是修改目标点或速度，而非受力。

选择建议：验证机器人能否从配合的行人身旁通过用 regular；面对无反应行人用 impassive；
目标静止条件下的接近行为用 surprised；最坏情况或对抗性行人用 threatening。

regular 亦是检验机器人位姿数据链路最直接的场景——机器人每 tick 均参与计算，故行人走出笔直
路线即表明链路中断。

## 4. 行为增益与端口

| 字段 | 生效条件 | 说明 |
|---|---|---|
| `social_force_factor` | 正常导航状态 | 缩放其他行人及通常情况下机器人的社交力，当前 Arena 默认 60.0。 |
| `goal_force_factor` | 有当前 waypoint 时 | 缩放朝目标期望速度收敛的力，默认 5.0。 |
| `obstacle_force_factor` | 有障碍采样时 | 缩放墙体/障碍物斥力，当前 Arena 默认 5.0。**行人贴墙时应调此项**。 |
| `other_force_factor` | 当前未接入 | 仅被保存并回传，当前 Regular 与特殊行为代码均不读取它，修改不会改变运动。 |
| `dist` | 含可见性判定的树 | 各树含义不同，见下。 |
| `duration` | 同上 | 每次触发后停留于特殊状态的秒数。 |
| `once` | 同上 | `true` 仅触发一次；`false` 每次重新进入均触发。 |
| `vel` | Scared / Curious 等读取该端口的树 | 特殊行为的速度参数；Surprised 不读取它，而是停止位置积分。 |
| `configuration` | 不生效 | 保持 0。 |

`dist` / `duration` / `once` / `vel` 在 **regular 下无效**，该树不含可见性与计时判定，
写入只会造成误解。

### Regular 行人的运动模型

每个 tick 的总力近似为：

```text
F_total = F_goal + F_social + F_obstacle + F_group
```

前三项的 factor 都是各自基础力的**线性乘数**。在位置、速度和周围环境完全相同的同一瞬间，
仅将某个 factor 翻倍，会使对应力项翻倍；但不同 factor 的数值不能横向当作实际受力比例，因为
它们乘的是不同函数：

```text
F_goal = goal_factor
         * (desired_direction * desired_velocity - current_velocity)
         / relaxation_time

F_obstacle = obstacle_factor
             * exp(-surface_distance / obstacle_sigma)
             * away_from_obstacle_direction

F_social = social_factor
           * sum(f(distance, relative_velocity, relative_angle))
```

LightSFM 当前固定 `relaxation_time = 0.5 s`、`obstacle_sigma = 0.2 m`。因此：

- `goal_force_factor: 5` 与 `social_force_factor: 10` **不表示**社交力恒为目标力两倍；
- 障碍力随表面距离指数衰减，远离墙体时即使 factor 较大也可能接近零；
- 社交力会对所有参与计算的 agent 求和，人数、距离、相对速度和方向都会改变基础力；
- factor 翻倍只保证该时刻对应力项翻倍，不保证速度、偏移距离或让行距离翻倍，因为下一 tick
  会基于新的位置和速度重新计算全部力。

Group force 使用 LightSFM 自身固定的 gaze/coherence/repulsion 参数，主要由 `group_id` 和组员位置
决定，不受上述四个 scenario factor 控制。

### 扫描、前视目标与穿墙风险

`look_ahead` 在 `dynamic` 每个行人的顶层配置，与 `desired_velocity` 同级。例如：

```yaml
desired_velocity: 0.8
look_ahead: 1.0
```

它只作用于 `NavigatePedestrians.py`：从 Isaac 人物当前位置，沿指向 HuNav 逻辑位置的方向
投影临时目标。默认 2.0 m，正数最小钳位至 0.35 m；零或负数回退 2.0 m。这样可避开
`Person.update()` 的 0.3 m 到点阈值。每次服务更新都重算目标，不是必须先走完这段距离才转弯；
速度仍来自 HuNav 的实际运动输出，小于等于 0.05 m/s 时清空目标并停止。它不改变 BT 的 `dist`。

静态障碍采样由 `arena_isaac/arena_isaac/arena_isaac/run_isaacsim.py` 的
`RaycastObstaclePublisher` 控制：72 个方向（间隔 5 度）、水平范围 4.5 m，高度为相对地面
`0.05, 0.15, 0.35, 0.60, 0.90, 1.20, 1.50, 1.80, 2.00 m`。当前假设 GRScenes 地面 z=0，
不再叠加人物出生偏移 z=1.25 m；每方向保留各高度中最近的命中点，供 `closest_obs` 使用。

普通行走每个 HuNav 周期都会计算合力，但 obstacle force 是软约束，且各命中点的障碍力取平均。
目标力、机器人/其他行人的力可能抵消墙体斥力；漏检、离散积分和 Isaac 人物跟踪误差也可能导致穿透。
当前尚无 sweep/overlap 硬碰撞回退，单纯提高 force factor 不能保证永不穿墙。

Surprised 激活时只调用 `lookAtTheRobot()`，不做正常位置积分，桥接侧同时强制输出零速度。
motion hold 期间不调用 ComputeAgents；恢复后 ComputeAgents/MoveAgent 的 dt 被限制在
`[0, 0.1] s`，避免将冻结期间累计时间一次积分，导致 duration 瞬间到期和行人跨越数米。

### 其他运动输入

除 force factor 外，行人轨迹还受以下参数和实时状态影响：

| 输入 | 影响 |
|---|---|
| `desired_velocity` | 正常导航的期望巡航速度；顶层 `velocity` 当前不参与计算。 |
| waypoint 的 `desired_velocity` | 覆盖“上一点到当前点”这一段的期望速度。 |
| `waypoints` | 决定目标方向、转弯和路线；急转弯可能产生圆弧或过冲。 |
| `radius` | 改变与机器人/行人的表面距离，越大越早产生社交避让。 |
| `goal_radius` | 决定何时切换 waypoint；实际阈值为该值加 0.1 m。 |
| `cyclic_goals` | 决定末点锁停或继续执行往返循环。 |
| `pose` yaw | 只决定出生朝向；运动后朝向由速度方向更新。 |
| 机器人与其他行人 | 位置、速度、半径、方向和数量共同决定 social force。 |
| 墙体/障碍采样 | 距离、方向和采样分布决定 obstacle force。 |
| `behavior_tree` / `type` | 可临时替换目标、速度或执行停止/逃离/阻挡，可能压过 Regular SFM。 |
| 仿真时间步 | 决定力积分为速度和位移的步长。 |

普通 `BTRegularNav.xml` 的建议排查与调参顺序：

1. 实际速度不对，先检查 `desired_velocity` 和逐段速度；
2. 路线或拐点不对，先检查 waypoint 几何；
3. 贴墙时调 `obstacle_force_factor`，不要用 social factor 代替；
4. 对机器人/其他行人反应不足或过强时，再调 `social_force_factor`；
5. 目标拉回不足或过强时调 `goal_force_factor`；
6. 每次只改一个参数，并同时观察 `sfm_forces` 中的 desired/social/obstacle 向量。

### `dist` 的含义

| 行为树 | 含义 | 检测半径 |
|---|---|---|
| Regular | 不使用 | 无判定 |
| Surprised | 检测半径 | `dist` |
| Scared | 检测半径 | `dist`（内层判定固定 3.0） |
| Curious | 停止距离 | 固定 10.0 |
| Threatening | 阻挡点前置距离 | 固定 4.5 |

threatening 下 `dist` 并非检测半径：小于 0.8 将直接碰撞机器人，大于 2.5 则前冲过远、不再
构成阻挡。

### 可见性判定的限制（仅含判定的树）

- 用中心到中心距离，不是到机器人路径的距离 —— 机器人绕大弯时行人可能中途退出分支，看起来像
  失去兴趣离开
- 要求机器人落在行人朝向 ±99.74° 以内（所有行人共用，不可配置），**不含射线检测**，墙后的
  机器人同样算可见
- 出生朝向来自 `pose`，背向机器人出生的行人需转向后才触发

### Threatening 行为特性

- 目标点每 tick 重算，所以行人是跟踪机器人而非瞄准固定拦截点；机器人绕行会被重新阻挡，分支
  不成立即返回原路线
- 追逐时速度被覆盖为固定 2.0 m/s，配置的 `desired_velocity` 无效
- 「机器人正前方」实际偏转 90°，行人从侧面切入（上游公式所致，**不要在本地改**，否则与其余
  threatening scenario 静默不一致；细节见 `实现细节.md`）
- `once: false` 会无限次重复拦截，机器人无法通过

## 5. 机器人字段

| 字段 | 说明 |
|---|---|
| `name` | 须与所管理的机器人一致。 |
| `pose` | 起点 `[x, y, yaw_deg]`。 |
| `waypoints` | 按顺序发送为 Nav2 goal；到达当前点后才发送下一点，最终点成功后 episode 才完成。 |
| `waypoint_tolerance` | 中间 waypoint 的 XY 到达半径（m）；未声明时为 0.25。 |
| `final_goal_tolerance` | 最终 waypoint 的 XY 到达半径（m）；未声明时为 0.25。 |
| `social_attributes` | `passive` \| `neutral` \| `aggressive`，见 §6。未声明时取 `neutral`。 |
| `social_yielding` | 主动让行流程开关。 |
| `desired_linear_vel` | 机器人 Social MPC 的场景级巡航速度覆盖（m/s）；reset 时覆盖 profile 的同名值。 |
| `behavior` | 纯文字，代码不读取。 |

机器人仍使用 `NavigateToPose` 逐段执行，而不是一次发送 `NavigateThroughPoses`。某一段
abort/cancel 会终止整条路线；中间 waypoint 的 success 不会触发 task reset 或提前保存采集
episode。旧格式 `start` / `goal` 会被视为只有一个 waypoint 的路线；若同时提供 `waypoints`
与显式 `goal`，则先按序访问 `waypoints`，最后访问 `goal`。

每段 goal 发布前，task generator 会先把对应值写入 Nav2
`goal_checker.xy_goal_tolerance`，等待参数更新成功后再发布目标。中间 `N-1` 个目标使用
`waypoint_tolerance`，最后一个目标使用 `final_goal_tolerance`；两者必须大于 0。当前
`yaw_goal_tolerance` 保持 `2*pi`，因此只检查 XY 位置，不要求 waypoint 的目标朝向。这里不对
tolerance 与相邻 waypoint 间距的关系做额外限制，由场景设计者自行决定。

`social_yielding` 优先级由高至低：launch 参数 → `robot.social_yielding` → `false`。
推荐在 `robot:` 块内声明该字段；旧版顶层 `social_yielding` 只在 robot 未声明时作为回退。

`desired_linear_vel` 只能写在 `robot:` 下，例如：

```yaml
robot:
  social_attributes: passive
  desired_linear_vel: 0.8
```

reset 时先下发 `social_attributes` profile，再下发 `desired_linear_vel`，所以场景值覆盖
profile 的巡航目标，但不改变 profile 的其他社交参数。它不是速度硬上限；实际输出还受
`weights_optimizer.max_linear_velocity` 和机器人 `model_params.yaml` 中的
`velocity_smoother_max_velocity[0]` 限制。当前三个 profile 的 MPC 上限和 Ai2_Bot2 的
smoother 上限均为 `0.8 m/s`，因此 `desired_linear_vel: 0.8` 可以作为目标速度生效，但实际
速度仍可能因转弯、障碍和社交代价低于该值。

启用 social yielding 后，LLM 选择的让行点 Y 只是临时 Nav2 goal，不属于 scenario 路线终点：

- 原始 goal 被 Y 抢占时产生的 `CANCELED` 不会判定 episode 失败；
- 到达 Y 产生的 `SUCCEEDED` 不会判定路线完成，也不会触发 `save_data`；
- re-yield 过程中所有临时 goal 的 terminal status 都会被忽略；
- orchestrator 恢复 scenario 的原始最终 goal G 后，RobotManager 才重新绑定 Nav2 action 状态；
- 只有 G 最终返回 `SUCCEEDED`，才发布路线级成功状态并保存 episode。

### Reset 后的 scene-ready 同步

Isaac 任务不会在 spawn 完成后立即放行机器人和行人。当前启动顺序为：

```text
reset_start
  -> 取消上一 episode 的 Nav2 goal，机器人持续输出零速度
  -> teleport robot，删除并重新 spawn 行人
  -> task_reset 发布当前 episode id，Isaac unpause
  -> 行人保持出生点，HuNav 暂停 ComputeAgents 积分
  -> 所有行人 animation graph 初始化完成
  -> animation graph 就绪后继续运行 0.75 s 仿真时间
  -> /isaac/scene_ready 发布当前 episode id
  -> RobotManager 收到 reset 后的新 local costmap，并确认其边界包含 base_link、LiDAR 和前深度相机原点
  -> RobotManager 发布 robot 原始 goal，随即发布最终 /scene_ready episode id
  -> 独立 motion hold 保持开启：Nav2 可以规划，但最终 robot cmd_vel 被强制置零，HuNav 也不积分
  -> Nav2 接受机器人 goal 并产生该 goal 之后的 fresh global plan
  -> proactive trigger 立即 pause，执行 snapshot + LLM replan
  -> orchestrator 验证让行点 Y，unpause 并发布 Y，但继续保持 motion hold
  -> 收到 fresh Y plan，等待 0.35 s 命令链稳定后解除 hold，robot 与 human 才开始运动
```

`/task_generator_node/task_reset`、`/isaac/scene_ready` 和最终的 `/scene_ready` 都使用
`std_msgs/Int16` 与 transient-local QoS。`task_reset` 保存当前 episode id；两个 ready topic 的 `-1`
都表示 gate 关闭。`/isaac/scene_ready` 只表示 Isaac 动画与仿真帧稳定；RobotManager 验证 local
costmap 和 sensor TF 后才发布最终 `/scene_ready`。HuNav、RobotManager goal gate 和 proactive trigger
只认最终 topic，且其非负值必须与当前 episode id 完全一致。采用 episode id 而非普通 Bool，是为了
避免 reset 后误读上一 episode 的 latched `true`，也避免节点较晚启动时漏掉首个 `task_reset`。
所有跨进程 gate（Isaac、HuNav、proactive trigger）都只由带 episode id 的 `task_reset` 驱动，
不订阅无 id 的 `reset_start`；否则两个 topic 跨进程乱序时，晚到的旧 `reset_start` 会把已经 ready
的新 episode 错误重置为 `-1`。RobotManager 在自己的 `reset()` 同步路径中直接关闭最终 gate、取消
旧 action 并清空 costmap readiness，因此 reset 期间仍不会提前放行。

稳定阶段内：

- RobotManager 会取消上一 episode 遗留的 `NavigateToPose` action，并持续向最终 `cmd_vel` 发布零速度；
- 新 episode 的原始 robot goal 尚未发布，因此 Nav2 不会提前驱动机器人；
- HuNav 不调用 `ComputeAgents`，逻辑行人位置不会提前积分；
- 发往 Isaac 的人物速度为零，人物只初始化 animation graph，不沿 waypoint 行走；
- local costmap 必须为本次 reset 后的新消息，并同时覆盖 `base_link`、`lidar_frame` 和
  `chassis_camera`；固定等待时间不会掩盖 rolling window 仍停在旧位姿的问题；
- costmap freshness 按 callback 相对 reset 边界的 `time.monotonic()` 到达顺序判断，不比较
  simulation time。仿真时间会暂停或在 episode reset 时回退，用它比较会把有效的新 costmap 误判为旧；
- snapshot 自己的 `delta_time=0` Replicator warmup 只负责渲染，不计入上述 0.75 s 稳定时间。

在 `social_yielding: true` 时，最终速度链为
`collision_monitor -> cmd_vel_pre_hold -> motion_hold_gate -> cmd_vel -> Isaac`。motion hold 不阻止
TF、costmap、planner 或 controller 运转，只把发往 Isaac 的每条速度命令替换为零，并让 HuNav 保持
冻结，因此 fresh global plan 可以在 robot 和 human 都没有离开初始位置时产生。reset 会重新上锁；
`social_yielding: false` 时 gate 透明透传。

排查时可同时观察：

```bash
ros2 topic echo /task_generator_node/task_reset
ros2 topic echo /isaac/scene_ready
ros2 topic echo /scene_ready
ros2 topic echo /social_yielding/motion_hold
ros2 topic echo /task_generator_node/Ai2_Bot2/goal_pose
ros2 topic echo /task_generator_node/Ai2_Bot2/plan
```

正常顺序应为同一个 episode id 的
`task_reset/hold=true -> isaac/scene_ready -> goal_pose -> scene_ready -> plan -> pause/snapshot -> Y -> hold=false`。
若有 `/isaac/scene_ready` 但没有最终 `/scene_ready`，查看 task generator 的
`Holding robot and pedestrian goals: scene gate ...` 日志。它会区分
`no-fresh-local-costmap`、`stale-local-costmap`、`no-TF:<target>-><sensor>` 和
`sensor-outside-local-costmap:<sensor>`。若 `/isaac/scene_ready` 本身没有出现，再检查 Isaac 中是否仍
有人物处于 bind/T-pose、人物 prim 是否存在，以及 animation graph 初始化是否报错。

因此开启让行不会把“到达让行点”误当作任务完成。若恢复 G 后导航 abort/cancel，则整条路线仍按失败
处理，数据 logger 会丢弃该次未完成 episode。

### Y Plan 与 LLM 配置

两个节点分别负责触发与执行：`proactive_yielding_trigger` 等待 ready、原始 goal 和完整 planner
`/plan` 后触发 pause/snapshot；`social_yielding_orchestrator` 负责 LLM 选点、验证、发布 Y、
等待到达以及恢复 G。不要用 MPC 裁剪后的 `received_global_plan` 代替完整 `/plan`。

发布 Y 前记录 plan 回调序号并清空缓存；只接受之后收到、frame 相同且终点距 Y 不超过 1.1 m
的 plan。该容差匹配当前 NavFn 1.0 m 搜索容差并留一格余量，不是最终停车精度。此处不比较
wall-time 的 goal 时间戳与 sim-time 的 plan 时间戳。8 s 内无匹配路径则保持 hold 并记录拒绝原因；
匹配成功后再等 0.35 s，让 controller/smoother 替换原 G 方向的命令。

到达临时 Y 的等待上限为 240 s（wall time）。reset 会递增 episode generation，旧 HTTP 请求
即使稍后返回，也不会继续旧重试循环、发布旧目标或释放新 episode 的 hold。

选点 prompt 在 `social_yielding_selector.py` 的 `PROMPT_TEMPLATE` / `FEEDBACK_TEMPLATE`。
当前模型为 `gpt-5.6-terra`，接口为 `https://llmapi.roboscience.xyz/v1/responses`，密钥从环境
读取。prompt 对较远点的偏好为软约束（约 1 至 5 m），不能替代 costmap 与深度校验。
`social_yielding: false` 时不会触发该 episode 的 LLM 选点，motion gate 透明透传；启动节点仍可能存在。

launch 参数为三态字符串（`auto` / `true` / `false`），`auto` 表示未指定。若既有脚本以
`social_yielding:=false` 表示「使用默认值」，应改为 `auto` 或不传，否则会覆盖 scenario 中的
`true`。

该字段实际不是 per-robot 的（由单个 latched topic 控制），多机器人时最后声明者生效，取值
冲突会触发告警。当前格式仅支持单个 `robot:`，暂无实际影响。

## 6. 社交 Profile

`social_attributes` 选定一组参数，于 reset 时下发至 controller_server，
无需重启即生效。

| 参数 | passive | neutral | aggressive | 说明 |
|---|---|---|---|---|
| `social_weight` | 700.0 | 550.0 | 400.0 | SFM social-work，计入速度与角度 |
| `proxemics_weight` | 150.0 | 110.0 | 70.0 | 个人空间气泡强度 |
| `proxemics_d0` | 0.8 | 0.7 | 0.5 | 气泡衰减尺度，不是硬碰撞半径 |
| `proxemics_alpha` | 3.0 | 3.0 | 3.0 | 峰值缩放，调强度请用 `proxemics_weight` |
| `social_clear_distance` | 2.0 | 1.5 | 1.0 | 硬截断，超出则完全跳过该行人 |
| `social_safety_distance` | 1.0 | 0.82 | 0.5 | 进入后 near-gain 生效 |
| `social_mid_gain` | 1.0 | 1.0 | 1.0 | |
| `social_near_gain` | 6.0 | 5.0 | 4.0 | |
| `max_linear_velocity` | 0.8 | 0.8 | 0.8 | vx **上限**，非巡航速度 |
| `desired_linear_vel` | 0.5 | 0.5 | 0.8 | 实际速度参数 |

三者只保留 `weights`、`weights_optimizer`、`trajectorizer`，公共 `global_social_layer` 覆盖
已移除，统一使用 `configs/nav2/nav2.yaml` 的 global costmap social layer。全局
costmap 已关闭 `obstacle_layer`，该层是规划器唯一的行人输入，缩小气泡会使全局路径过于贴近
行人，导致 MPC 持续与自身路径冲突。

`max_linear_velocity` 仅为优化器的解上界，不构成速度目标（目标是 `desired_linear_vel`），
提高它本身不会使机器人加速；且 velocity_smoother 另有一道不受 profile 影响的钳位
（当前 0.8），设为更大值不会生效。

**选择建议。** passive 制动早而频繁，较难产生实质交互协商；aggressive 基本按既定路线通行。
需要机器人对行人确有反应又不至于难以推进时选 neutral。注意其巡航 0.5 相对典型 0.3–0.4 的
行人速度差很小，设计超越类场景时需留意（见 §7）。

`social_clear_distance` 宜保持较大以便提前反应，同时调低增益，而非相反。

### 修改约束

- **仅纳入行人相关参数。** 不得写入 `obstacle_weight` 或 `inflation_radius`，这两项为所有
  障碍物共用，会改变机器人对墙体的处理。
- **三个 profile 须定义相同的 key。** 切换时仅下发目标 profile 中存在的 key，独有的 key 会
  保留前一次的值。
- **新增 profile 目录需重新编译**（符号链接按文件建立，非按目录）；修改既有文件不需要。
- 每次仅调一个参数；需查看各项代价时开启下面的 `[MPC-DIAG]` 开关。

### Footprint、距离与诊断配置

下表为当前配置快照，修改后以运行时参数为准：

| 参数 | 当前值与意义 | 文件 |
|---|---|---|
| robot `footprint` | local/global 都取 `${footprint}`；模型定义经 scale 替换为有效多边形，随机器人姿态旋转 | `configs/nav2/nav2.yaml`、`arena_robots/arena_robots/robots/Ai2_Bot2/model_params.yaml` |
| `footprint_padding` | local/global 均 0.0 m；不再用 robot_radius 替代该多边形 | `configs/nav2/nav2.yaml` |
| `inflation_radius` | local/global 均 0.50 m，障碍物周围的膨胀距离，不是机器人半径 | 同上 |
| `cost_scaling_factor` | local/global 均 2.0；越大软代价随距离衰减越快 | 同上 |
| HuNav `radius` | 0.42 m，行人自己的 SFM 身体半径 | `arena_bringup/configs/hunav/default.yaml` |
| HuNav robot radius | 0.45 m，行人眼中的 robot SFM 半径，与 Nav2 footprint 独立 | `task_generator/.../simulators/human/hunav/hunav.py` 的 `_create_robot_message()` |
| `obstacle_weight` | 0.03，MPC 对 local costmap 的软代价权重，不是碰撞半径 | `configs/nav2/controllers/social_mpc/controller_config.yaml` |
| `optimizer.diagnostics_enabled` | false，关闭每秒 `[MPC-DIAG]` WARN；不修改权重或其他 WARN | 同上 |

多边形用于二维水平包络，不能表示不同高度上的空隙；完整模型投影也只覆盖测量时的固定收臂姿态。
`inflation_radius` 可以大于 footprint 的内切半径：致命障碍栅格、内切碰撞带和外侧软膨胀代价不是同一概念。
不能把整片可见膨胀区都当作 lethal，也不能仅凭中心栅格可通行断定完整模型安全。

恢复诊断时把 `optimizer.diagnostics_enabled` 改成 true 并重启 controller；该开关当前在配置时读取，
不是动态参数。`debug_optimizer` 只控制 Ceres 调试，两者独立。日志的 `cost` 为
`0.5 * residual²`，是优化目标贡献，不是对机器人直接施加的物理转向力。

## 7. 交互场景设计

交互源于速度差与几何关系，而非单一参数。

- **超越** 要求机器人在行人后方且实际更快。aggressive 巡航目标为 0.8 m/s，passive/neutral 为
  0.5 m/s；应比较实际速度而非仅比较配置上限，受阻减速后可能不再具备超越条件。
- **对向** 要求同一走廊内朝向相反，且双方有足够助跑距离。
- **交叉** 要求两条路径同一时刻汇于同一点，可用各自速度与距离反推。
- **出生间距** 至少 `robot_radius + ped_radius`（当前 HuNav 近似值为 `0.45 + 0.42 = 0.87 m`）。重叠出生自
  第 0 tick 起结果即无意义。修改位姿前应对照占据栅格图，图面上「空」的走廊可能已在膨胀层内。

## 8. 生效性验证

不应以 RViz 标签文字为依据——后缀直接由 `behavior.type` 拼接，无论逻辑是否执行均会显示，
仅能证明配置已被解析。

| 检查项 | 命令／位置 | 含义 |
|---|---|---|
| 机器人位姿是否进入 hunav | `ros2 topic echo <ns>/robot_states` | 位置非零且持续变化 |
| 特殊分支是否真的执行 | `<ns>/human_states` 的 `agents[0].behavior.state` | `== 1` 即该周期已执行 |
| 行人是否对机器人反应 | `sfm_forces` 的蓝色箭头（`socialForce`） | 单行人场景下机器人是唯一贡献者，箭头随接近而增长 |
| threatening 是否进入追逐 | 观察速度 | 明显超出 `desired_velocity`（覆盖为 2.0） |
| 机器人侧速度与代价 | 开启 `optimizer.diagnostics_enabled` 后看 `[MPC-DIAG]` | 下发／实测速度、巡航目标、上限、各 critic 代价 |

修改 scenario 或 profile 无需重新编译。修改 Isaac 侧 Python 代码同样无需编译，但需重启
Isaac 进程。
