## 相机安装参数

`postprocess/process_raw_to_dataset.py` 顶部：

```python
ROBOT_MODEL      = "Ai2_Bot2"   # 从哪个 model_params.yaml 读 scale
CAMERA_FORWARD_M = 0.3506       # +x，机器人原点前方（未缩放）
CAMERA_LATERAL_M = 0.0          # +y，左侧（未缩放）
CAMERA_HEIGHT_M  = 1.6453       # +z，机器人原点上方（未缩放）
CAMERA_PITCH_DEG = 30           # 俯仰角，向下为正

ROBOT_SCALE, _ = _read_robot_scale()                            # 从 yaml 读，不是常量
CAMERA_HEIGHT_CM = round(CAMERA_HEIGHT_M * ROBOT_SCALE * 100)    # = 132，派生值
```

**三个偏移都是未缩放的原始 USD 值**，缩放系数从
`arena_robots/robots/<ROBOT_MODEL>/model_params.yaml` 的 `scale` 读取 —— 那里本来就是它的唯一
出处（USD `xformOp:scale`、sensor TF、footprint、`robot_radius` 都按它缩放）。改机器人缩放只改
yaml，这边自动跟随。**不要在这里复制一份 scale**，也不要把缩放后的结果写死：两份副本改一处
另一处就悄悄不同步。

找不到 yaml 或解析失败时回退 1.0 **并打 WARN** —— 缩放错了是静默的几何错误，所以宁可报出来，
不猜 0.8。

`CAMERA_HEIGHT_CM` 是派生的，不再手工维护，所以目录名（`observation.images.rgb.132cm_30deg`）
不可能和实际计算用的几何对不上。`annotate_with_instructions.py` 从这里 import。

### 与 USD 的核对结果

从 `robot_usds/humanoid/Ai2_Bot2/Ai2_Bot2.usda` 的
`head_link2/head_camera/d435/head_camera` 解出：

| 量 | USD 实测 | 结论 |
|---|---|---|
| 旋转 | 与 `T_ROBOT2CAMERA @ pitch_matrix(30)` 差 **6.7e-16** | 轴约定与 pitch 都吻合 |
| hFOV | `focalLength 10.4775` + `verticalAperture 15.71625` → 恰好 **90.00°** | 与 `--hfov` 默认值一致 |
| scale | 0.8（`model_params.yaml`，经父 Xform 作用于整个引用） | → `ROBOT_SCALE` |

**俯角 2026-09-01 从 15° 改为 30°**（USD commit `27997ec`）。同一次改动里父级
`head_camera` Xform 被钉成单位变换，安装偏移移到 Camera prim 自己身上（`translate (0.2, 0, 0)`）,
所以 `CAMERA_FORWARD_M` / `CAMERA_HEIGHT_M` 那两个常量**尚未针对新结构核对过** —— base USD 是
二进制 crate，没有 `pxr` 绑定时解不出完整变换链。原值 (0.3506, 0, 1.6453) 是在旧结构下解出并用
真实采集数据验证过的（相机高度实测 1.3169 m,差 0.7 mm）。新结构下需要用一次新采集重新验证：
比对 `pose.*` 的 z 平移是否仍是 1.3162 m 左右。
| hFOV | **90.0°**（focalLength 10.4775 / aperture 20.955） | 与 `--hfov 90.0` 吻合 |

核对旋转时要先套上采集侧的 USD→ROS optical 转换（右乘 `diag([1,-1,-1])`），否则对不上。

**前提假设**：`head_joint1`/`head_joint2` 在采集期间不动，偏移才是常量。两个 joint 的
`state:angular:physics:position` 都是 0 且 drive 刚度很高，应该不动 —— 但这一点**未在运行时
验证**。如果头部会在 episode 中转动，偏移就不再是常量，必须改为从记录的位姿反解。

### cam_to_robot_footprint 必须带平移

```python
def cam_to_robot_footprint(pitch_deg):
    return np.linalg.inv(mount_matrix() @ T_ROBOT2CAMERA @ pitch_matrix(pitch_deg))
```

**`mount_matrix()` 曾经不存在。** `T_ROBOT2CAMERA` 和 `pitch_matrix` 都是纯旋转，两个纯旋转
相乘求逆还是纯旋转 —— 平移列全零。于是 `extrinsics @ cam_to_robot_footprint()` 只改朝向，平移原样透传，
算出来的"机器人位姿"和相机位姿逐位相同（实测 `max abs diff = 0.0`），恒定偏差 0.28 m。

这种错不会报任何异常：位姿差一个固定偏移，看起来完全合理。

修复后往返验证：由已知机器人位姿构造 extrinsics，再用 `cam_to_robot_footprint()` 还原，10 个位姿最大
误差 **2.2e-16**（浮点极限）。

### 采集分辨率

`data_logger_replicator.py` 顶部：

```python
CAPTURE_WIDTH = 640
CAPTURE_HEIGHT = 480
```

这一个常量被用三次：初始 render product、reset 后重建的 render product、以及
`process_camera_data()` 把 `cameraProjection` 换算成像素内参时的 width/height。三者必须是同一
组数，所以只留一个常量 —— render product 按一个尺寸建、内参按另一个尺寸算，会得到与实际图像
不符的 fx/fy/cx/cy，而且图看起来完全正常。**曾经这三处是三个写死的 1280×720。**

## 阶段 1：几何标注

`process_raw_to_dataset.py`。合并了原来的 `raw_data_convert.py` + `gen_pixel_goal_labels.py`
（两者已删除），一遍完成，省掉一次 depth PNG 的写-读循环，也保证 PNG 和标注用的是同一份
depth 数据。

```bash
# 整个 grscenes 根目录，所有 world
python process_raw_to_dataset.py --data-path src/social_gen/traj_data/grscenes

# 单个 world
python process_raw_to_dataset.py --data-path src/social_gen/traj_data/grscenes/grscenes_1
```

耗时 ~10 分钟 / 100 episodes。

### 处理顺序

1. 读 `videos/episode_XXXXXX_N.npy`（按 N 数字排序，不是字典序）和 `data/episode_XXXXXX.json`
2. 从相机位姿推机器人位姿 → 离散化动作（前进/左转/右转/停）
3. 写 RGB PNG、depth PNG、preview mp4
4. **校验 PNG 确实落盘**，数量对不上就报错退出，避免生成半套数据集
5. 用内存里的 depth（不重读 PNG）算 pixel goals
6. 写 parquet 和 `meta/`
7. 清理原始输入：raw npy **和** `data/episode_XXXXXX.json`（`--keep-src` 可保留）

### Pixel Goal 算法

Farthest Visible Goal（Wei et al. 2025）。投影的是**机器人脚印**（地面位置），不是相机中心：

```python
for j in range(frame_idx + 1, end):          # 往后找最远的可见点
    p_world = [robot_xy[j][0], robot_xy[j][1], ground_z, 1.0]  # 脚印，强制到地面
    if np.hypot(*(p_world[:2] - here_xy)) < min_ground_dist:
        continue                              # 太近的跳过（默认 0.5m 水平距离）
    p_cam = T_w2c @ p_world
    z = p_cam[2]
    u, v = fx * p_cam[0] / z + cx, fy * p_cam[1] / z + cy
    if z > depth[v, u] + margin:              # 遮挡检测
        continue
    best = ((u, v), j - frame_idx)
```

为什么投影脚印而非相机中心：不同俯仰角的相机看同一位置，投影相机中心会因高度抵消而重叠。
InternData-N1 验证过，投影脚印误差 2-5px，投影相机中心误差 106px。脚印也才是机器人真能驶到
的位置，符合导航任务的定义。

**代码曾经并没有这么做。** `farthest_visible_goal` 投的是 `extrinsics[j][:2,3]`，也就是相机
自己的 xy，只把 z 压到地面 —— 这正是本节说要避开的那种做法。

要注意这是**两个叠加的错误**，得分开看：

1. 投影点取的是相机轨迹而不是机器人轨迹
2. `cam_to_robot_footprint()` 当时没有平移，所以"机器人轨迹"其实还是相机轨迹（见上一节）

也就是说光加 `robot_xy` 参数并不会改变任何输出 —— 传进去的和原来那个是同一组数（实测
`max abs diff = 0.0`）。必须先修 `mount_matrix()`，`robot_xy` 才真正指向脚印。

修好之后用本机实际参数（640×480、hFOV 90°、当时俯仰 15°、相机在原点前 0.2805 m 高 1.3162 m）实测
两者偏差：

| 目标距离 | 脚印 v | 相机轨迹 v | 偏差 |
|---|---|---|---|
| 1 m | 575（出画） | 488 | 87 px |
| 2 m | 372 | 346 | 26 px |
| 4 m | 265 | 258 | 7 px |
| 8 m | 210 | 208 | 2 px |

近处差得多、远处收敛，因为 0.28 m 的安装偏移相对目标距离越来越小。1 m 处脚印已经投到画面外
（v=575 > 480），这符合几何：正下方的地面不在 15° 俯角的视野里。

> 上表是在 **15° 俯角**下实测的。改成 30° 后同一批数字会变（盲区 1.31 m → 0.84 m,1 m 处的
> 脚印不再出画），但结论不变：投相机中心而非脚印在近处会偏几十像素。

`farthest_visible_goal` 新增 `robot_xy` 参数，由调用点传 `xyyaw[:, :2]`（即
`extrinsics @ cam_to_robot_footprint()` 的平移）。签名上它有默认值 `None`，不传会回退到相机
轨迹**并打 WARN** —— 保留回退是为了让老调用点不至于直接崩，但那条路径产出的标签是错的。

验证：直线前进的 episode 里 goal 的 u 恒为画面中线 320、v 全部落在 240 以下（脚印在地面必然
投到下半部）。

### 汇总输出

```
==========================================================================
SUMMARY   camera 132cm_30deg   (CAMERA_HEIGHT_CM / CAMERA_PITCH_DEG)
==========================================================================
  grscenes_1                   converted    3  skipped    0  failed   0, meta/ covers 3
  grscenes_9                   converted    1  skipped    0  failed   1, meta/ covers 1
--------------------------------------------------------------------------
  3 world(s): 5 converted, 0 already done, 1 failed
  25 frames, 0 pixel goals this run

  1 FAILURE(S) -- episode and reason:
    grscenes_9/episode_000001: ValueError: need at least one array to stack
```

单条失败不中断整批。失败的 episode 保留 raw npy，修好原因后重跑会自动只捡它。失败列表在
结尾重复一遍，免得被前面的滚屏埋掉；traceback 走 stderr，带具体行号。

已转换的判据是原始输入还在不在（转换成功会清理 npy 和 `data/episode_XXXXXX.json`）。所以指着
根目录反复跑只处理新数据。

**删除有两道闸**：parquet 必须能读回、且行数与刚写入的一致，否则抛错并保留原始数据。写一半的
parquet（比如磁盘写满）不会连带把原始数据一起带走。原始数据只有这一份，删了要重跑 Isaac。

**用了 `--keep-src` 之后自动跳过就失效了。** 判据是"npy 没了"，而 `--keep-src` 恰好把它留着，
所以下次重跑会把那个 episode 重新编码一遍（输出相同，白花时间）。整目录重跑即可，不必特殊处理。

删掉 json 前有两样东西必须先搬走，否则永久丢失：**相机内参**（`observation.camera_intrin`,现存
入 `info.json` 的 `camera_settings`；本机是 hFOV 90° + 640×480 的标准值 fx=fy=320 / cx=320 /
cy=240,也可反推）和**行人轨迹**（`observation.peds_state`,现存入 parquet 的 `pose_peds` 列）。

`meta/` 描述的是整个数据集，不只是本次转换的。重跑新增 episode 时，会把已转换 episode 的
parquet 读回来合并（length、动作分布、n_goals 都能从 parquet 恢复），否则第二次跑会
把之前的 episode 从 `info.json` 和 jsonl 里删掉。

json 删掉后 `flat_episodes()` 认不出这个 world（它就是靠那些 json 识别 world 布局的），所以还按
`meta/` 或 `data/chunk-*/` 的存在判定"已转换"—— 否则旧的 session 扫描会把 `data/`、`meta/`、
`videos/` 各当成一个 world。

## 阶段 2：语义标注

`annotate_with_instructions.py`。读阶段 1 产出的 preview mp4，调 Gemini 生成 R2R 风格的导航
指令，写进 `meta/`。

### 复用已有 instruction

默认读 `meta/episodes.jsonl`，已有真实 instruction 的直接复用，只为缺的付费。视为"不存在"因而
会重试的有三种：阶段 1 写的 `PLACEHOLDER_INSTRUCTION`、旧格式的
`Navigate from start to destination...` 开头，以及 `FAILED_GENERATION_EP*`。要全部重新生成加
`--redo`。

### 扫描范围

扫 `videos/chunk-*/preview/` 所有 chunk，不只 `chunk-000`，`CHUNK_SIZE = 1000`。

## 目录结构

一个 world 一个数据集，没有 scenario 层也没有时间戳层。重跑同一个 world 会接着已有 episode
往后编号，不覆盖。

```
src/social_gen/traj_data/grscenes/<world>/
  data/
    episode_000000.json                      采集产物：相机参数 + 行人状态
    chunk-000/episode_000000.parquet         阶段 1 产物：带 pixel goals
  videos/
    episode_000000_0.npy                     采集产物：每帧一个，内含 rgb + depth
    chunk-000/
      observation.images.rgb.132cm_30deg/
        episode_000000_0.png                 uint8 RGB
      observation.images.depth.132cm_30deg/
        episode_000000_0.png                 uint16 毫米（1000 = 1m）
      preview/
        episode_000000_rgb.mp4               8-bit h264，阶段 2 的输入
  meta/
    info.json                                阶段 1 写，阶段 2 更新 total_tasks
    episodes_stats.jsonl                     阶段 1 写
    tasks.jsonl                              阶段 2 写：去重后的 instruction
    episodes.jsonl                           阶段 2 写：episode → instruction
  snapshots/
    2026-08-24_14-30-05/                     让行快照：head/back/topdown PNG + depth npy
```

`snapshots/` 是 proactive yielding 的产物，不是数据集的一部分，但也跟着 `world` 走，和
`data/`、`videos/` 同层。后处理不会误扫它 —— world 目录是靠 `data/episode_*.json` 认的。

它由 `save_snapshots:=true|false`（**默认 false，即不保留**）控制：

```bash
arena launch sim:=isaac robot:=Ai2_Bot2 world:=grscenes_1 \
    tm_robots:=scenario tm_obstacles:=scenario save_data:=true \
    social_yielding:=true save_snapshots:=true
```

**这个参数不是"不抓快照"。** 让行的 replan 是从磁盘把快照读回去的（selector 读三张 PNG，
`pixel_to_map` 读 `<cam>_depth.npy` + `<cam>_camera.json`），快照不落盘等于让行不可能发生。
唯一能安全可选的是**读完之后是否保留**，所以 `false` 只在每次 replan 结束后删掉对应那个目录。
再让行（re-yield）会重新抓一份，所以删除时机不影响多轮让行。

默认不保留：一次采集会让行很多次，每次三张 PNG + 一个 depth npy，replan 读完之后就是纯增长。
调让行管线时加 `save_snapshots:=true` —— 快照是 LLM 当时"看到什么才选了这个让行点"的唯一记录。

原始文件和转换产物共用 `data/` 和 `videos/`，靠 `chunk-XXX` 这一层区分，不会撞名。

`videos/` 下的 npy 每帧一个，文件名里没有 rgb/depth 的区分位，所以一个文件里装两种模态
（`{"rgb", "depth"}` 的 dict），读的时候需要 `allow_pickle=True`。自采数据没问题，但别拿这个
loader 去读外来的 npy。

### parquet 列

```
action                                int32     -1 无动作 / 0 停 / 1 前进 / 2 左转 / 3 右转
pose.132cm_30deg                      4x4 f32   相机位姿（世界系），不是机器人位姿
goal.132cm_30deg                      [u,v] i32 pixel goal，无效为 [-1, -1]
relative_goal_frame_id.132cm_30deg    int32     goal 在几帧之后，无效为 -1
pose_peds                             struct    {p_1: [16 f32], p_2: ...}，每人一个展平的 4x4
timestamp                             float32
frame_index                           int64     每个 episode 从 0 重新开始
index                                 int64     跨整个数据集连续
episode_index / task_index            int64
```

**dtype 分两类**：内容列（`action`、`goal`、`relative_goal_frame_id`）是 int32,LeRobot 记账列
（`frame_index`、`index`、`episode_index`、`task_index`）是 int64。这是参考格式的划分，值域远在
int32 内（像素 < 2^15、帧号 < 2^20）。

**`frame_index` 和 `index` 是两个计数器**：前者每个 episode 归零，后者跨数据集连续。某个 episode
的 `index` 起点取决于它前面所有 episode 的长度，单个 episode 转换时算不出来，所以先按 episode 内
序号填，再由 `write_meta()` 统一回填偏移。

**无效 goal 用哨兵值 `-1` 而不是 null**，筛选要用 `goal[:,0] >= 0`；判 `is None` 一个都筛不出来。

**`pose_peds` 曾被静默丢列**：值读进了 `out_data`，但 `peds_type` 留成 `None` 导致 schema 不声明
该字段，`pa.Table.from_pydict` 按 schema 建表时直接丢掉。行人轨迹只存在于 raw json 里，而 json
转换后会被删除 —— 这个 bug 曾让整个数据集的社交信号无法恢复。现按首帧推断 struct 类型。

**`pose.*` 存的是相机位姿**（`observation.camera_state` 原样透传），因为那才是实际测量值。
机器人位姿是 `extrinsics @ cam_to_robot_footprint()` 算出来的中间量，只用于动作离散化和脚印
投影，不落盘 —— 需要的话按上面公式自己算，两者差一个安装偏移（本机 0.2805 m 前 / 1.3162 m 上）。

## 参数详解

### process_raw_to_dataset.py

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--data-path` | 必需 | grscenes 根目录或单个 world 目录 |
| `--hfov` | 90.0 | 水平 FOV（度）。**仅在数据缺 `observation.camera_intrin` 时**用来推 intrinsics |
| `--depth-scale` | 1000.0 | PNG 单位/米，**必须 1000** |
| `--flip-v` | False | 翻转 v 坐标 |
| `--fps` | 30.0 | 采集帧率，写入 timestamp 和 meta/，并决定 `--fwd-speed-thresh` 的换算 |
| `--fwd-speed-thresh` | 0.05 | 前进判定的**速度**阈值（m/s），除以 fps 得到逐帧位移 |
| `--fwd-thresh` | 无 | 已弃用：直接给逐帧位移（米）。给了就覆盖上面那个 |
| `--yaw-speed-thresh-deg` | 8.0 | 转弯判定的**角速度**阈值（度/秒），除以 fps 得到逐帧角度 |
| `--yaw-thresh-deg` | 无 | 已弃用：直接给逐帧角度（度）。给了就覆盖上面那个 |
| `--lookahead` | 5.0 | Goal 搜索的**弧长**预算（米），不是帧数 |
| `--margin` | 0.2 | 遮挡检测松弛量（米） |
| `--min-ground-dist` | 1.0 | 排除比这更近的脚印（米） |
| `--ground-z` | 0.0 | 地面平面的世界 z |
| `--depth-is-euclidean` | False | depth 存的是径向距离而非平面深度时才加 |
| `--instructions` | | 注入外部 instruction 的 JSON |
| `--keep-src` | False | 转换后保留 raw npy **和** `data/episode_XXXXXX.json` |

### intrinsics 从记录里读，不再从 hfov 推

采集侧把相机自己的 `cameraProjection` 解出的 K 写进了每帧的 `observation.camera_intrin`，主点
是从矩阵里读的并做过 aperture-offset 修正。后处理优先用这个值。

`--hfov` 只是没有该字段时的回退，它假设**主点在图像正中**。USD 相机设了 aperture offset 时
主点会偏出几十个像素，用 hfov 重算会静默破坏每一次反投影 —— 图看着仍然正常，pixel goal 全错。
回退时会打 WARN，日志里搜 `no observation.camera_intrin` 能看到。

**曾经这里完全没读记录值**，一律按 `--hfov 90.0` 重算。在此之前转换过的数据 pixel goal 都是
错的，需要重跑（删掉 `data/chunk-*/`、`videos/chunk-*/`、`meta/`，raw npy 若已清理则无法恢复）。

### 前进阈值按速度给，不按逐帧位移

`discretize_actions` 比较的是相邻两帧之间的单步位移，所以"位移阈值"离开帧率就没有意义：
0.05 m/帧 在 30 fps 下等于 **1.5 m/s**，远超室内机器人常见的 0.3–0.8 m/s，会把每一个真实
前进帧判成 STOP。因此阈值改成速度（`--fwd-speed-thresh`，默认 0.05 m/s），由 `--fps` 换算。

启动时会把换算结果打出来，两种单位都给，便于确认：

```
  action threshold: forward > 0.00167 m/frame (= 0.050 m/s at 30.0 fps), turn > 5.0 deg/frame
```

`--fwd-thresh` 仍然接受直接给逐帧位移，用于复现旧行为，给了会打 NOTE 提示等价速度。

**曾经 STOP 标签根本不会出现**：`np.where(~turning & (forward <= fwd_thresh), FORWARD, step)`
两个分支都是 FORWARD，是个恒等操作，静止帧被标成 FORWARD。已改为 STOP。这个 bug 同时掩盖了
上面的阈值问题 —— 所有帧都是 FORWARD 时看不出阈值失效。修 STOP 而不修阈值，结果会反过来变成
几乎全是 STOP。

### annotate_with_instructions.py

| 参数 | 说明 |
|---|---|
| `--data-path` | 必需，grscenes 根目录或单个 world 目录 |
| `--use-vlm` | 调 VLM 生成，需要 `API_KEY` 环境变量 |
| `--instructions` | 用预生成的 JSON，跳过 VLM |
| `--redo` | 重新生成已有的 instruction（默认复用） |

### depth_scale 必须 1000

float32 米 ↔ uint16 PNG 的换算因子。

| 阶段 | 操作 | 公式 |
|---|---|---|
| 采集 | float32 → uint16 | `depth_mm = depth_m * 1000` |
| 阶段 1 写 PNG | uint16 → PNG | 直接写，已经是 mm |
| 阶段 1 标注 | uint16 → float32 | `depth_m = depth_mm / 1000` |

采集侧 `process_depth_for_png()` 已经乘过 1000，所以 `write_depth_pngs()` 对整型输入直接透传。
**曾经这里乘了第二次**，2000 mm × 1000 截断到 65535，整张深度图全饱和压平 —— 已修。

对不齐的后果：标注用 100 → 深度偏 10 倍 → 遮挡检测全失败；用 10000 → 偏 0.1 倍 → 所有点都被
判为"太近"。

### depth_is_euclidean 保持 False

区分 depth PNG 存的是哪种距离。

| 值 | 含义 | 遮挡检测用 |
|---|---|---|
| False（默认） | 平面深度 z（`distance_to_image_plane`） | `z = p_cam[2]` |
| True | 径向距离 r（`distance_to_camera`） | `r = norm(p_cam[:3])` |

采集侧用的是 `distance_to_image_plane`（见 `data_logger_replicator.py` 的 `self.depth_annot`），
所以保持默认 False。

针孔反投影 `X = (u-cx)*Z/fx` 需要的是 Z 而不是 r。r/Z 的比值在画面中心是 1.00、边缘中点 1.41、
角落 1.52 —— 搞错会吃掉 `--margin 0.2` 的全部容错，边缘尤其严重。调 margin 之前先确认这个。

### flip_v

Isaac 相机若 +Y 朝上（OpenGL 约定），投影后需要翻 v：`v = h - 1 - v`。

采集侧 `process_camera_data()` 里右乘 `np.diag([1.0, -1.0, -1.0, 1.0])` 已转成 ROS optical
（+Y down）。是否还需要 `--flip-v` 属于经验值，**尚未实证验证**（见文末[已知未验证项](#已知未验证项)）
—— 如果 goal 点整体上下颠倒就是这里。

### lookahead 和 margin

- `lookahead`（5.0 m）：沿路径累计**弧长**的预算，不是帧数。用弧长而非直线距离是因为它单调 ——
  超预算后面不可能再有候选点，循环可以直接 `break`；直线距离在机器人绕回来时会变小，所以
  `min_ground_dist` 那一项只能 `continue`
- 早先的 `--max-lookahead`（64 帧）已删除。帧数在慢速场景里等价的距离太短：实测 0.335 m/s 时
  64 帧只有 0.69 m，还没出近处盲区（当时 15° 下是 1.31 m），产出 0 个 goal
- `margin`（0.2m）：`z > measured + margin` 才判遮挡。goals 太少（大量 -1）就加大，试 0.5
- **`min_ground_dist`（1.0 m）在 30° 下才真正起作用。** 俯角决定近处盲区：h=1.32 m、480 px 高时
  地面进入画面的位置是 `h / tan(pitch + atan((H-cy)/fy))` 加上安装前移量

  | 俯角 | 盲区（相机） | 盲区（机器人原点） | 地平线 v | 可见地面带 |
  |---|---|---|---|---|
  | 15° | 1.03 m | 1.31 m | 154 | 68% 画面高 |
  | **30°（当前）** | **0.56 m** | **0.84 m** | **55** | **88% 画面高** |

  15° 时 1.0 m 的阈值是 no-op —— 比它更近的点早被投影测试拒掉（实测 0.5 / 1.0 / 1.31 输出逐位
  相同，1.5 才开始起作用）。30° 下盲区缩到 0.84 m,所以 1.0 m 变成了真正的约束

## Instruction 的来源与格式

### 推荐流程

采集时不生成 instruction，阶段 1 用 placeholder 占位，阶段 2 让 VLM 看 preview 视频后直接写进
`meta/`。不需要中间 JSON 文件。

```bash
python process_raw_to_dataset.py --data-path <grscenes>          # placeholder
python annotate_with_instructions.py --data-path <grscenes> --use-vlm   # 填真的
```

### 阶段 1 的优先级链

如果你想在阶段 1 就注入 instruction，优先级是：

1. `--instructions` 指定的 JSON
2. `episode_XX/instruction/instruction.json`（旧采集结构才有）
3. placeholder `"PLACEHOLDER_INSTRUCTION"`

`--instructions` 可以给单个文件，也可以给目录 —— 给目录时按 `<world>.json` 自动匹配，适合多
world 批量。

```json
{ "0": "Walk forward past the sofa...", "1": "Turn right at the doorway..." }
```

键是 episode index 的字符串形式。

### meta/ 里的最终格式

`tasks.jsonl` —— 去重后的 instruction，一行一条：

```json
{"task_index": 0, "task": "Walk forward past the sofa and stop at the doorway."}
```

`episodes.jsonl` —— episode 到 instruction 的映射：

```json
{"episode_index": 0, "tasks": ["Walk forward past the sofa..."], "length": 150}
```

`episodes_stats.jsonl` —— 每个 episode 一行，逐 feature 的统计，遵循 LeRobot v2.1 形状：

```json
{"episode_index": 0, "stats": {
  "action": {"min": [-1], "max": [3], "mean": [1.5399], "std": [0.9327], "count": [576]},
  "pose.132cm_30deg": {"min": [[...4x4...]], "max": [...], "mean": [...], "std": [...], "count": [576]},
  "goal.132cm_30deg": {"min": [-1, -1], "max": [367, 476], "mean": [...], "std": [...], "count": [576]},
  "relative_goal_frame_id.132cm_30deg": {...}, "timestamp": {...},
  "frame_index": {...}, "episode_index": {...}, "index": {...}, "task_index": {...}}}
```

三条容易写错的规则：

- 所有统计值**包在 list 里**，标量也是 `[v]`；`count` 是 `[行数]`,不是 feature 的元素个数
- 归约是**逐元素**沿帧轴做的，所以 4×4 的 pose 得到 4×4 的逐元素均值，不是整个矩阵一个数
- 整数列的 `min`/`max` 保持整型（`[-1]` 而非 `[-1.0]`）,只有 `mean`/`std` 是浮点；`timestamp`
  是浮点列所以四个都是浮点

统计从 parquet 现算，所以早先转换的 episode 和刚转的一视同仁 —— 这也是原始 npy 已删还能重建
`meta/` 的原因。

`info.json` —— `features` 块从 parquet schema 现读生成，避免声明和数据脱节：

```json
"action":  {"dtype": "int32",   "shape": [1],    "names": ["action_index"]},
"pose.132cm_30deg": {"dtype": "float32", "shape": [4, 4], "names": ["pose.132cm_30deg"]},
"timestamp": {"dtype": "float32", "shape": [1], "names": null}
```

记账列（`timestamp`、`frame_index`、`episode_index`、`index`、`task_index`）的 `names` 为 null,
内容列带 `names`,`action` 用 `["action_index"]`。`fps` 是 int（`30`,不是 `30.0`）,`total_videos`
为 0 —— rgb/depth 是逐帧静态图，没有任何 feature 的 dtype 是 video。

`pose_peds` 在参考格式里没有对应写法（那个数据集没有行人）。它是 struct,而格式里没有 struct
dtype,现按 `float32 / shape [2,16] / names ["p_1","p_2"]` 渲染 —— 2 个行人 × 展平的 4×4。这是
最贴近的写法，不是参考里的定义。

**`task_index` 必须由阶段 2 回写进 parquet。** 阶段 1 转换时 instruction 还不存在，`task_index`
一律写 0;而 `tasks.jsonl` 会给不同 instruction 分配不同 index。只更新 meta 不回写 parquet 的话，
按 parquet 取 instruction 的 loader 会把 episode 0 的指令配给所有 episode。阶段 2 现在同步三处：
parquet 的 `task_index` 列、`episodes.jsonl`、`episodes_stats.jsonl`。`info.json` 的 `total_tasks`
同样由阶段 2 更新。

### 只想更新 instruction，不想重跑转换

只跑阶段 2 就行，它只改 `tasks.jsonl`、`episodes.jsonl` 和 `info.json` 的 `total_tasks`，PNG 和
parquet 不动。要换成一批新的 instruction 就加 `--redo`。

## 常见问题

**preview mp4 报 `TypeError: TiffWriter.write() got an unexpected keyword argument 'fps'`**

缺 `imageio[ffmpeg]` 后端。imageio 找不到 ffmpeg 时会错误地回退到 tifffile 插件去处理 `.mp4`。
装 `imageio-ffmpeg` 即可。

**depth PNG 全是 65535**

depth 被乘了两次。检查 `write_depth_pngs()` 是否对整型输入直接透传 —— 采集侧已经是毫米了。

**action 里没有 STOP / 全是 STOP**

两个不同的历史问题。全无 STOP 是那个恒等 `np.where` 的锅（已修）；全是 STOP 说明 `--fwd-thresh`
被当成逐帧位移传了一个按速度理解的值。看启动打印的那行 `action threshold`，它把两种单位都给了。

**pixel goals 全是 -1**

按顺序查：机器人这条 episode 是不是真的动了（看 action 分布，别只看 `--fwd-speed-thresh`）；
`--margin` 加到 0.5 试试；`--min-ground-dist` 是不是把近处全滤掉了（短轨迹尤其容易，总位移不足
0.5m 时一个 goal 都不会有）；depth 语义是不是搞成了径向距离（边缘误差 1.52 倍）；
`--flip-v` 反了导致投影点全落到画面外。

**让行不工作，日志说 snapshot dir not found**

查是不是把 `save_snapshots` 理解成了"抓不抓"。它只控制 replan 读完之后删不删，不影响抓取。
如果目录在 replan 开始前就不存在，那是采集侧的问题（`[Snapshot] ABORT` 会说明原因：机器人
prim 还没 spawn，或 `model_params.yaml` 里没有 `snapshot` 块）。

**`--use-vlm` 报缺 API_KEY**

`export API_KEY=sk-...`。只从环境变量读，源码里不硬编码。

**阶段 1 报 PNG 数量不符**

故意的。写完 PNG 会校验数量，对不上就停，避免留下半套数据集。先查磁盘空间和写权限。

**验证数据集完整**

`meta/` 四个文件都在；`tasks.jsonl` 里不是 placeholder；parquet 能读；
`relative_goal_frame_id.132cm_30deg` 的 valid 数量不为 0。

## 已知未验证项

改动集中在标签几何上，下面几条**尚未在真实 Isaac 采集数据上跑过**，只有构造数据的验证：

- **`--flip-v`** 是否需要，仍属经验值。采集侧 `process_camera_data()` 已右乘
  `np.diag([1,-1,-1,1])` 转成 ROS optical（+Y down），按理不需要再翻。若 goal 点整体上下颠倒
  就是这里。定这个的办法：放一个已知位置的标记物，手工投影，和 depth 图对照。
- **头部关节不动**这个前提（`head_joint1`/`head_joint2`）。若头部会在 episode 中转动，安装偏移
  就不是常量，必须改为从记录位姿反解。
- **采集分辨率改成 640×480 之后**没有真机跑过。`CAPTURE_WIDTH/HEIGHT` 只保证代码三处一致，
  USD 相机侧是否也是 640×480 需要另行确认 —— 不一致时内参会和图像不符，而图看着正常。
- **snapshots 跟随 world + `save_snapshots`** 的落盘路径与删除逻辑，需要跑一次带让行的采集
  才能确认。
