# Arena 常见问题

## Isaac 容器：修改 `isaacsim_msgs` 后为什么要重建镜像？

### 现象

在 `arena_isaac/isaacsim_msgs` 里新增或修改 `.srv` / `.msg` 后，Isaac 侧启动报错，例如：

- `cannot import name 'SpawnUsdRobot' from 'isaacsim_msgs.srv'`
- 路径指向 `/opt/isaac_bridge_msgs/...`（Python 3.11 的 site-packages）

而在 **arena 主容器**里已经 `colcon build` 过 `isaacsim_msgs`，错误仍然存在。

### 原因

Isaac 仿真容器使用的镜像由 `src/Arena/_meta/docker/features/isaac/Dockerfile` 构建。构建过程会：

1. 在 **builder 阶段**把仓库里的 `arena_isaac/isaacsim_msgs` 拷进镜像；
2. 用 **Python 3.11** 单独执行 `colcon build --packages-select isaacsim_msgs`；
3. 将产物安装到最终镜像的 **`/opt/isaac_bridge_msgs`**。

Isaac Sim 内置环境依赖这套与 **Isaac 自带 ROS2 bridge** 匹配的 Python 3.11 消息包，运行时应优先从镜像内的 **`/opt/isaac_bridge_msgs`** 加载 `isaacsim_msgs` / `hunav_msgs` / `arena_people_msgs`，**不会**安全地复用你在宿主工作区里额外编出来的 `install_py311_msgs/` 或 `/opt/arena_ws/install` 产物。

因此：只改源码并在 arena 容器里编译 **不够**，必须 **重新构建 `arena_isaac` 镜像**，把新的接口编进 `/opt/isaac_bridge_msgs`。

> 经验结论：`install_py311_msgs/` 若是基于宿主侧另一套 ROS toolchain（例如 Humble）构建，即使 Python 版本匹配，也可能在 Isaac 服务创建阶段因为 `rclpy` / typesupport / FastCDR ABI 不一致而直接崩溃。现在推荐路径是：**Isaac 只用镜像内 `/opt/isaac_bridge_msgs`，宿主 eval overlay 继续按需使用 `install_humble_eval/`。**

### 操作步骤

在项目根目录（`arena_ws`）下，保证与平时 `source arena` 一致的环境变量（如 `HOST_ARENA_WS_DIR`、`ARENA_PROJECT_NAME` 等），然后执行：

```bash
# 1. 重建 Isaac 镜像（一般即可）
docker compose \
  -f src/Arena/_meta/docker/docker-compose.yaml \
  --project-directory "$(pwd)" \
  --project-name "${ARENA_PROJECT_NAME:-arena-$(basename "$(pwd)")}" \
  build isaac
```

若 Docker 仍命中旧缓存、接口未更新，可强制从头构建消息包阶段：

```bash
docker compose \
  -f src/Arena/_meta/docker/docker-compose.yaml \
  --project-directory "$(pwd)" \
  --project-name "${ARENA_PROJECT_NAME:-arena-$(basename "$(pwd)")}" \
  build isaac --no-cache
```

```bash
# 2. 用新镜像重新创建并启动 Isaac 容器
docker compose \
  -f src/Arena/_meta/docker/docker-compose.yaml \
  --project-directory "$(pwd)" \
  --project-name "${ARENA_PROJECT_NAME:-arena-$(basename "$(pwd)")}" \
  up -d isaac --force-recreate
```

若已 `source arena`，也可使用：

```bash
arena_docker_compose build isaac
arena_docker_compose up -d isaac --force-recreate
```

### 何时需要重做上述步骤？

- 在 `arena_isaac/isaacsim_msgs` 下 **新增、删除或修改** `.srv`、`.msg`、`.action`；
- 或拉取他人包含上述改动的代码后，本地 Isaac 仍报 **旧符号 / 无法 import 新类型**。

arena 主容器内对 `isaacsim_msgs` 的 `colcon build` 仍建议保留，用于 **task_generator 等节点**（ROS Jazzy / 工作区 `install`）；Isaac 容器则 **必须**通过镜像重建同步同一套接口定义。

### 相关文件

- Isaac 镜像定义：`src/Arena/_meta/docker/features/isaac/Dockerfile`
- Compose 服务名：`isaac`（`src/Arena/_meta/docker/docker-compose.yaml`）
- Isaac launch 环境注入：`src/Arena/arena_bringup/launch/simulator/sim/isaac/isaac.launch.py`

### 当前推荐环境组合

| 组件 | 推荐来源 | 原因 |
|------|----------|------|
| Isaac 容器内 Python 3.11 ROS 消息包 | `/opt/isaac_bridge_msgs` | 与 Isaac 5.1 自带 Jazzy bridge ABI 对齐 |
| 宿主/arena 容器评测 overlay | `install_humble_eval/` | 避免 Ubuntu 22.04 上的 glibc 版本不匹配 |
| 视频编码校验 | `ffmpeg` + `imageio` | `internnav_eval` 会优先写 H.264，必要时转码并用 `ffprobe` 复核 |

## 启动与验证

### 基本启动流程

```bash
# 1. 在宿主机进入工作区并启动 arena 容器
cd ~/arena_ws
source arena

# 2. 在 arena 容器内启动仿真（Isaac 模式）
arena launch sim:=isaac robot:=Ai2_Bot2
```

### 使用 USD 机器人模型

目前已配置 USD 加载的机器人：

| 机器人 | 模型目录 | 驱动方式 |
|--------|----------|----------|
| `Ai2_Bot2` | `arena_robots/robots/Ai2_Bot2/Ai2_Bot2.usd` | 差速（differential） |
| `LinkHou_S2` | `arena_robots/robots/LinkHou_S2/LinkHou_S2.usd` | 全向（holonomic） |

两者都是 **USD-only** 机器人（没有 URDF），只能在 Isaac 仿真器下使用。

#### 启动 Ai2_Bot2

```bash
arena launch sim:=isaac robot:=Ai2_Bot2
```Link

#### 启动 LinkHou_S2

```bash
arena launch sim:=isaac robot:=LinkHou_S2
```

#### 其它常用参数

```bash
arena launch sim:=isaac robot:=Ai2_Bot2 \
  world:=map_empty \
  local_planner:=dwb \
  headless:=0
```

- `world`：地图名称，默认 `map_empty`
- `local_planner`：局部规划器（`dwb`、`teb`、`mpc` 等）
- `headless`：`0` 全部显示，`1` 仅 RViz，`2` 无 GUI

### 验证 USD 加载是否正常

启动后在日志中确认以下关键信息：

1. **USD 路径被正确发现**（task_generator 日志）：

   ```
   Spawned USD robot 'robot0' via SpawnUsdRobot
   ```

2. **Isaac 侧 SpawnUsdRobot 服务执行成功**（Isaac 容器日志）：

   ```
   [SpawnUsdRobot] === Starting spawn: name=Robots/robot0, ns=robot0 ===
   [SpawnUsdRobot] USD loaded at /World/Robots/robot0
   [SpawnUsdRobot] Articulation root at: /World/Robots/robot0/...
   [SpawnUsdRobot] Namespace remap complete: N attributes updated
   [SpawnUsdRobot] === Spawn complete: /World/Robots/robot0 ===
   ```

3. **ROS2 话题正常**：

   ```bash
   ros2 topic list | grep robot0
   ```

   应看到 `/robot0/cmd_vel`、`/robot0/odom`、`/robot0/laser_scan` 等话题。

4. **使用 RViz2 和 rqt 进行可视化检查**：

   启动后可以在 arena 容器内打开 RViz2 查看 TF 树、激光扫描、机器人模型等：

   ```bash
   rviz2
   ```

   在 RViz2 中可添加以下 Display 进行验证：
   - **TF**：查看坐标系树是否完整（`odom` → `base_footprint` → 各传感器 frame）
   - **LaserScan**：话题设为 `/robot0/laser_scan`，确认激光数据正常
   - **RobotModel**：确认机器人描述是否正确加载

   使用 rqt 检查消息和节点关系：

   ```bash
   # 查看节点图（话题连接关系）
   rqt_graph

   # 查看 TF 树结构
   ros2 run tf2_tools view_frames

   # 实时监控特定话题的消息频率
   ros2 topic hz /robot0/odom

   # 查看话题内容
   ros2 topic echo /robot0/odom --once
   ```

### 常见启动问题排查

| 现象 | 可能原因 | 处理方式 |
|------|----------|----------|
| `cannot import name 'SpawnUsdRobot'`（Isaac 侧） | Isaac 镜像未重建 | 参考上方「修改 isaacsim_msgs 后重建镜像」 |
| `Could not load model of type(s) USD` | `Robot.py` 未注册 `ModelProvider_USD` | 检查 `arena_robots/Robot.py` 是否 import 并注册了 `ModelProvider_USD` |
| `USD model ... not found in ...` | install 目录缺少 `.usd` 文件 | 重新 `colcon build --symlink-install --packages-select arena_robots` |
| `service "arena" is not running` | 容器入口脚本异常退出 | 检查 `docker logs arena-arena_ws-arena-1`，参考 `.installed` 是否含不可用 feature |
| Isaac 容器启动后立即退出 | 缺少 NVIDIA 驱动或 GPU 资源 | 确认 `nvidia-smi` 正常，Docker 已配置 `nvidia-container-toolkit` |

## `internnav eval` 运行后不结束，或卡在 episode 内

### 优先排查项

1. 检查 `/clock` 是否真的在前进：

   ```bash
   ros2 topic echo /clock --once
   ```

2. 检查 Nav2 planner service 是否存在：

   ```bash
   ros2 service list | grep get_path
   ros2 lifecycle nodes
   ```

3. 检查 `finished` topic 的 QoS：

   ```bash
   ros2 topic info /robot0/finished -v
   ```

### 常见根因

- **Gazebo 时钟桥接失败**：sim time 停在 `0`，导致 episode timeout 不触发。
- **Nav2 插件名写法与 ROS 发行版不匹配**：在 Jazzy 下，`planner_server` / `behavior_server` / `recoveries_server` 的插件类名要写成 `nav2_navfn_planner::NavfnPlanner`、`nav2_behaviors::Spin` 这类 `::` 形式；若仍写成旧的 `/` 形式，会出现插件存在但无法加载的报错。若你运行的是 Humble，则相反，需要保留旧的 `/` 写法。
- **结束信号 watcher QoS 不匹配**：`finished` 使用 `TRANSIENT_LOCAL` 时，`ros2 topic echo --once` 可能收不到结束消息。

### 已采用的稳妥做法

- `task_generator` timeout 同时支持 sim time 与 wall clock。
- `internnav_eval.py` 使用自定义 Python watcher 订阅 `finished`，显式设置 `RELIABLE + TRANSIENT_LOCAL`。
- Gazebo 时钟桥接延迟启动，降低 `parameter_bridge` 提前连不上仿真的概率。

## `task_generator_node` 异常退出或疑似死锁

### 典型现象

- 日志停在 `Task Reset!` 前后。
- 进程最终 `SIGABRT` / `exit code -6`。
- 同时 `planner_server` 或相关 Nav2 service 没有真正 ready。

### 根因

`task_generator` 若在持有 `asyncio` 锁时进入 `is_done`，而 `is_done` 内部又同步等待 Nav2 service，会形成锁内阻塞。只要 planner service 没起来，就会把 reset 流程卡死。

### 修复原则

- 不要在持锁期间调用可能阻塞的 Nav2 service 路径。
- 将 reset 主逻辑抽成 unlocked 版本复用。
- 在 `_check_task_status()` 中先判断是否需要 reset，再进入真正的 reset 流程。

## ROS Humble 下 `cv2` / `numpy` 导入报错

### 现象

- `numpy.core.multiarray failed to import`
- `AttributeError: module 'numpy' has no attribute 'float'`

### 原因

- ROS Humble 环境中的 `cv2` 往往仍依赖 NumPy 1.x ABI。
- `tf_transformations` / `transforms3d` 旧实现还可能引用已经废弃的 `np.float`。

### 建议处理方式

```bash
/usr/bin/python3 -m pip install --user 'numpy<2'
```

- 评测 recorder 中，优先使用纯 Python 的四元数转欧拉角实现，避免对 `tf_transformations` 的运行时依赖。
- 改完后可先做最小验证：

```bash
/usr/bin/python3 -c "import cv2, numpy; print(cv2.__version__, numpy.__version__)"
```
